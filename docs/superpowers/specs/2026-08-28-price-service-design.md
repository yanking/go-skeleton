## 0. 已定决策

下列六项由用户逐条拍板,是本设计的前提,不再重开:

| 议题 | 决定 |
|---|---|
| 数据落点 | 只落库,不出查询口;消费方直接读库 / 读 Redis |
| 存储粒度 | 只有 K 线入库;ticker/depth 只在 Redis 留最新值 |
| 入口形状 | 无参 = 常驻采集;另有 `instruments` 与 `backfill` 子命令 |
| depth 语义 | 固定档位快照,不维护本地订单簿 |
| 订阅来源 | 三层叠加:交易所全量 → instruments 表;实际订阅 → subscriptions 表;yaml 管连接参数与首次导入过滤 |
| REST 触发 | 子命令手工触发,常驻进程另在重连后自动补洞 |

## 1. 边界

| 拥有 | 不拥有 |
|---|---|
| 交易所连接与订阅的生命周期 | 下单、账户、任何私有流(全部走公共流,不需要密钥) |
| K 线历史的完整性(无洞) | 全量订单簿重建 |
| 最新 ticker / 浅层盘口快照 | 对外查询接口 |
| 交易所方言到中立表示的翻译 | 跨交易所指数 / 合成定价 |

**一个后果要先说清:表结构与 Redis key 就是事实上的对外契约。** 这与 AGENTS.md
「model 不出服务边界」相左——那条约定的前提是有 gRPC 出口挡在前面,而这里没有。
所以改表 = 破坏性变更,得按契约对待。

## 2. 领域模型

只谈语义与键,不谈 DDL。

| 实体 | 唯一键 | 作用 |
|---|---|---|
| instrument | (交易所, 市场, 原生 symbol) | 交易所全量交易对的本地镜像,是「能订什么」的权威范围。下架的标 delisted 而不删行——历史 K 线还引用着它 |
| subscription | (交易所, 市场, 原生 symbol, 流类型, 周期) | 「实际订什么」。一行 = 一条流;ticker/depth 行的周期为空 |
| kline | (交易所, 市场, 原生 symbol, 周期, 开盘时间) | 唯一入库的时序数据。带来源标记(ws 收线 / REST 补洞),排查时能分辨 |
| latest | Redis key | ticker 与盘口的最新值,无历史 |

### 归一化层存在的全部理由

| 差异 | Binance | OKX |
|---|---|---|
| symbol 形态 | `BTCUSDT` | `BTC-USDT` |
| 周期大小写 | `1m` / `1h` / `1d` | `1m` / `1H` / `1D`(大写) |
| 市场区分 | 换域名(现货与合约不同 host) | 同一连接,靠 instType 区分 |

**上表三行的具体取值与第 10 节同属待核实。** 写在这里是为了说明差异的*类型*——
「两家的 symbol 形态不同」这个事实是稳的,「OKX 周期用大写 H/D」这个取值不是。
设计依赖前者,实现依赖后者。

**中立类型里不出现任何一家的方言**,翻译只发生在交易所包内。这条是后面所有正确性的
地基——一旦方言漏进中立层,补洞的时间对齐和去重键就会在某一家上悄悄错位。

## 3. K 线正确性

三条规则,顺序不能变:

1. **只有已收线的 K 线入库。** 两家都给了「这根是否已收线」的标志位(Binance 在
   `k.x`、OKX 在 candle 数组末位的 `confirm`——字段名按第 10 节核实)。未收线的那根
   每秒都在变,落库等于把一根未完成的柱子当历史。
2. **一律 upsert,不 insert。** 同一根 K 线会从两条路径到达(ws 收线、REST 补洞),
   重复是常态而非异常。
3. **冲突时以 REST 为准**(后写覆盖)。两条路径的值本应相同;真不同时,REST 是交易所
   的最终账本,ws 帧可能是重连窗口里的中间态。

时间一律 UTC 毫秒、**以开盘时间为准**——收盘时间在跨周期换算时会引入边界歧义
(一根 1m 线的收盘时间等于下一根的开盘时间)。

## 4. 缺口检测与补洞

这是「只落库不出查询口」这个选择下最要紧的一块:没有查询口,消费方发现不了洞,
只能靠采集侧保证。

**触发点只有一个抽象:连接进入可用状态。** 进程启动、断线重连、订阅集变更后重建
——三者对补洞是同一件事,不分开写。

```
last = SELECT max(open_time) FROM klines WHERE (交易所, 市场, symbol, 周期)
起点 = last 存在 ? last + 一个周期 : now - 配置的最大回溯窗口
从起点分页拉到 now,逐页 upsert
```

| 现实 | 处理 |
|---|---|
| 分页上限各家不同,且现货/合约端点还不一样 | 页大小由交易所包声明,编排层只管翻页,不写死数字 |
| OKX 历史端点返回倒序,且「近期」与「历史」是两个端点 | 交易所包内统一成正序输出,编排层看不到这个区别 |
| REST 有权重/频次配额,补洞会瞬间打满 | 交易所包声明自己的限速,补洞按令牌桶取用;配额**全进程共享**——常驻补洞与 `backfill` 子命令同时跑时必须共用一个桶,否则一起被限流 |
| 回溯窗口无上限时,新标的首次补洞会拉几年数据 | 配置给最大回溯窗口,超出部分要人显式跑 `backfill` |

## 5. 连接模型与背压

**分组:** 同一 (交易所, 市场) 下的订阅合并进尽量少的连接,按该交易所的单连接订阅数
上限切分。上限值由交易所包声明。

**背压按数据语义分开**,这是整个采集侧最关键的一个设计:

| 流 | 队列满时 | 理由 |
|---|---|---|
| kline | 阻塞上游读取 | 收线帧丢一帧就是一个洞,而洞只能靠 REST 补回来。宁可让读取变慢 |
| ticker / depth | 丢弃最旧的 | 它们是快照,语义上只有最新一帧有意义;下一帧很快就到。为一帧过期快照阻塞住同连接上的 kline,是拿不可恢复的换可恢复的 |

如果三类流混在一条连接上而队列不分开,depth 的洪流会连带把 kline 拖住——所以
**队列必须按流类型分,不能按连接分**。

**乱序:** 同一连接内交易所保证有序,不做额外处理。跨重连有一个极短窗口可能收到旧
快照,直接覆盖即可——下一帧就纠正了,为此引入 CAS 写入不划算。

## 6. 最新值的陈旧语义

Redis 里的 ticker/depth **不设 TTL**,但每条值带两个时间戳:交易所事件时间、
本地接收时间。

理由:设了 TTL,断流后 key 消失,消费方看到的是「没有这个标的」;不设 TTL,消费方
看到的是「有这个标的,但数据是 3 分钟前的」。后者才是真相,而且这两种情况消费方的
处置完全不同——前者该报配置错误,后者该报采集故障。陈旧判定的阈值属于消费方的策略,
不该由采集方用 TTL 替它决定。

## 7. 故障矩阵

| 故障 | 行为 | 数据后果 |
|---|---|---|
| ws 断线 | 指数退避 + 抖动重连,上限封顶;重连后重订阅并触发补洞 | K 线无洞(补回);ticker/depth 断流期间为陈旧值 |
| 单条订阅被拒(标的已下架) | 从本次连接计划剔除并告警,其余订阅照常 | 一条坏订阅不拖垮整条连接 |
| REST 限流 | 按交易所返回的退避提示等待;令牌桶全进程共享 | 补洞变慢,不丢 |
| PG 不可达 | kline 写入重试,队列阻塞;持续失败即告警 | 不丢(代价是最终阻塞读取,这是刻意的) |
| Redis 不可达 | ticker/depth 直接丢弃并计数 | 只影响最新值,K 线链路不受牵连 |
| 交易所定时强制断连 | 与普通断线同一路径 | 同上 |

**注意最后一行的设计含义:没有一条「正常关闭」的特殊路径。** 交易所定时踢连接是常态,
把它当异常处理就会写出两套逻辑;当作普通断线,重连路径每天都被真实演练。

## 8. 两个子命令

| 命令 | 语义 | 幂等性 |
|---|---|---|
| 无参 | 常驻采集,实现组件生命周期,随信号优雅停机(停止重连 → 关连接 → 等在途 kline 落盘) | — |
| `instruments` | 拉全量交易对 upsert;交易所不再返回的标 delisted | 可重复跑,结果收敛 |
| `backfill` | 按显式区间分页拉 + upsert,跑完退出 | 可重复跑、可与常驻并行(共享限速桶) |

`backfill` 不依赖常驻进程,是因为它的典型用途恰恰是**常驻进程不在的时候**:
新接一个标的、事故后补数据。

## 9. 不变量

1. 只有已收线的 K 线入库。
2. K 线写入一律 upsert,唯一键含交易所与市场——不同交易所的同名标的是不同序列。
3. 时间一律 UTC 毫秒、以开盘时间为准。
4. 交易所方言(symbol 形态、周期大小写、分页方向、限速规则、连接上限)不出交易所包。
5. kline 不可丢,ticker/depth 可丢——两者的背压策略必须不同。
6. REST 配额全进程共享,常驻与子命令共用一个桶。
7. 连接进入可用状态就触发补洞,不区分首启 / 重连 / 重建。

## 10. 待核实项

协议细节按现有认知写,**实现时必须对着两家的当期文档逐条核实**,不能凭这份设计里的
数字下手:

- 单连接订阅数上限
- 订阅报文的频次限制
- 心跳周期,以及谁 ping 谁
- REST 分页上限与权重计算
- 历史端点的时间参数是闭区间还是半开
- 收线标志位的字段名与取值(Binance `k.x`、OKX `confirm`)
- 周期与 symbol 的确切拼写(尤其 OKX 周期的大小写)
- 历史端点返回的排序方向
- 浅层盘口流的档位与推送频率写法

这些是各家会改、且改了就**静默出错**的东西——不会报错,只会让数据悄悄少一段。
